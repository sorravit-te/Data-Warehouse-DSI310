# Task 4 — การคิดเชิงวิพากษ์และความท้าทายด้าน Data Engineering

## 4.1 การนำเข้าและรวมข้อมูล (Data Ingestion & Integration)

Chinook และ Northwind ต่างก็บันทึกข้อมูลการขาย แต่ schema ของแต่ละระบบถูกออกแบบแยกจากกัน จึงใช้ชื่อ
โครงสร้าง ชนิดข้อมูล และความหมายทางธุรกิจที่ต่างกัน การรวมข้อมูลต้องทำให้ความต่างเหล่านี้เป็นมาตรฐานเดียวกัน
โดยยังคงรักษา grain ของ `FactSales` ไว้: 1 แถวต่อ 1 รายการสินค้าในธุรกรรมการขาย

| ความท้าทาย | ตัวอย่าง | วิธีจัดการ |
| --- | --- | --- |
| ชนิดข้อมูลต่างกัน | `Customer.CustomerId` ของ Chinook เป็น `INTEGER` ส่วน `Customers.CustomerID` ของ Northwind เป็น `TEXT` | แปลงทั้งสองฝั่งให้เป็นรหัสอ้างอิงชนิด `TEXT` ปลายทางเดียวกัน และใช้การแปลงแบบเดียวกันทั้งใน dimension และ foreign key ของ fact |
| Primary key ชนกัน | รหัสลูกค้า พนักงาน หรือสินค้าจากสองระบบที่บังเอิญเหมือนกัน ไม่ได้แปลว่าเป็น entity เดียวกัน | ใช้รหัสมาตรฐานที่เติม prefix ตามต้นทาง เช่น `CHINOOK:<id>` และ `NORTHWIND:<id>` |
| ชื่อและโครงสร้างต่างกัน | `InvoiceLine` และ `Order Details` ต่างก็ป้อนข้อมูลเข้า `FactSales`; `Track` และ `Products` ต่างก็ป้อนข้อมูลเข้า `DimProduct` | ใช้เอกสาร Source-to-Target Mapping ที่ระบุชัดเจน พร้อม join และการแปลงเฉพาะของแต่ละต้นทาง แทนการเปลี่ยนชื่อคอลัมน์แบบง่ายๆ |
| Attribute ขาดหายหรือไม่สมมาตรกัน | Northwind ไม่มีอีเมลลูกค้า; Chinook มี `GenreName` และ `Composer`; Northwind มี `CategoryName` | เก็บ attribute ปลายทางที่ไม่มีข้อมูลเป็น `NULL` ห้ามสร้างค่าขึ้นมาเอง |
| การระบุตัวพนักงาน | Northwind ใช้ `Orders.EmployeeID` โดยตรง; Chinook เข้าถึง `Employee` ผ่าน `Customer.SupportRepId` | ตีความ Northwind ว่าเป็นการระบุพนักงานที่รับผิดชอบออเดอร์โดยตรง ส่วน Chinook เป็น support representative ที่ดูแลลูกค้ารายนั้น และต้องเทียบผลวิเคราะห์พนักงานโดยคำนึงถึงความหมายที่ต่างกันนี้ |
| ความสอดคล้องของ Measure | ทั้งสองต้นทางมี `UnitPrice` และ `Quantity` ระดับบรรทัด; Northwind มี `Discount` เพิ่มมาด้วย | ใส่ `SalesQuantity` จาก `Quantity` และคำนวณ `SalesAmount = UnitPrice * Quantity` สำหรับทั้งสองต้นทาง ส่วน `Discount` ของ Northwind ไม่นำมาคิดใน `SalesAmount` ตามที่โจทย์นี้กำหนด |
| วันที่และคุณภาพข้อมูล | `Invoice.InvoiceDate` และ `Orders.OrderDate` ให้วันที่ธุรกรรม; คีย์ การอ้างอิง รายการ วันที่ จำนวน และราคา อาจไม่ผ่านการตรวจสอบความถูกต้องได้เช่นกัน | แปลงวันที่ที่ถูกต้องเข้าสู่ `DimTime` ที่ใช้ร่วมกัน คำนวณ `DateKey = YYYYMMDD` และตรวจสอบคีย์ การอ้างอิง รายการซ้ำ ค่า NULL วันที่ และการแปลงชนิดข้อมูล ก่อนโหลดเข้าระบบ |
| แหล่งที่มาของข้อมูลและขนาดข้อมูล | `DimSourceSystem` ระบุว่าเป็น Chinook หรือ Northwind ต้นทางมี `InvoiceLine` 2,240 แถว และ `Order Details` 609,283 แถว | ใส่ค่า `SourceSystemID` ในทุกแถวของ fact เก็บ lineage ไว้ และวางแผนขนาดงาน ingestion ให้เหมาะสม โดยไม่ตีความปริมาณข้อมูลว่าเป็นผลประกอบการทางธุรกิจ |

การแปลงรหัสมาตรฐานต้องเหมือนกันทุกที่ที่รหัสนั้นปรากฏ ตัวอย่างเช่น รหัสลูกค้า
`CHINOOK:59` ใน `DimCustomer` ต้องปรากฏเป็น `CHINOOK:59` เช่นเดียวกันใน
`FactSales.CustomerID` ที่เกี่ยวข้อง กฎเดียวกันนี้ใช้กับรหัสพนักงานและรหัสสินค้าด้วย

ขั้นตอนตรวจสอบความถูกต้องควรยืนยันว่าแต่ละบรรทัดต้นทางไม่ซ้ำกัน มีการอ้างอิงที่จำเป็นครบถ้วน
วันที่ธุรกรรมแปลงได้ถูกต้อง และค่า `Quantity` กับ `UnitPrice` ใช้งานได้จริง ข้อมูลที่ไม่ถูกต้องควรถูกบันทึก log
และจัดการอย่างชัดเจน แทนที่จะโหลดเข้าระบบโดยสร้างวันที่ รหัส measure หรือ attribute เชิงบรรยายขึ้นมาเอง

ปริมาณข้อมูลที่ต่างกันของแต่ละต้นทางอาจทำให้ต้องใช้ขนาด batch หรือตารางเวลาการทำงานที่ต่างกันใน
production pipeline จริง แต่ทั้งสองเส้นทางการนำเข้าข้อมูลต้องรักษารหัส grain ของ fact measure
และกฎด้านคุณภาพข้อมูลให้เหมือนกัน

## 4.2 การรองรับการเปลี่ยนแปลงของ Schema (Schema Evolution)

หาก OmniCorp เข้าซื้อกิจการบริษัทที่สาม สิ่งแรกที่ต้องตัดสินใจคือข้อมูลการขายของบริษัทนั้น
เป็น business process เดียวกันและอยู่ใน grain ระดับ line-item เดียวกันหรือไม่ ถ้าใช่ ก็ใช้ `FactSales`
และ conformed dimension เดิมซ้ำได้เลย แต่ถ้าต้นทางนั้นเป็น process หรือ grain ที่ต่างออกไป
อาจเหมาะสมกว่าที่จะสร้าง fact table แยกต่างหาก

| การเปลี่ยนแปลง | แนวทางรองรับ | เหตุผล |
| --- | --- | --- |
| Source system ใหม่ | เพิ่มสมาชิกใหม่ `3 = ThirdCompany` เข้าไปใน `DimSourceSystem` | `FactSales.SourceSystemID` เดิมสามารถระบุธุรกิจใหม่ได้ โดยไม่ต้องแก้โครงสร้าง fact table |
| รหัสอ้างอิงจากต้นทางใหม่ | ขยาย namespace ด้วย `THIRDCOMPANY:<source id>` | Prefix ช่วยป้องกันการชนกัน พร้อมทั้งยังคงตรวจสอบย้อนกลับไปหาต้นทางได้ |
| ชื่อหรือการ join ที่ต่างกัน | สร้างเอกสาร Source-to-Target Mapping ชุดใหม่ | โครงสร้างเฉพาะของต้นทางใหม่ควรถูกแปลงให้เข้ากับแนวคิดที่ warehouse ยอมรับแล้ว |
| ลูกค้า พนักงาน สินค้า และวันที่ ที่เข้ากันได้ | ใช้ `DimCustomer`, `DimEmployee`, `DimProduct`, และ `DimTime` เดิมซ้ำ เมื่อความหมายตรงกัน | Dimension ที่ใช้ร่วมกันช่วยให้วิเคราะห์ข้ามธุรกิจได้ และเลี่ยงการสร้าง dimension ซ้ำซ้อนสำหรับแนวคิดเดียวกัน |
| Attribute ที่ขาดหายหรือเป็นของใหม่ | ใช้ `NULL` เมื่อ attribute ไม่มีข้อมูล และเพิ่ม attribute แบบ nullable เฉพาะเมื่อมีคุณค่าในการวิเคราะห์ชัดเจนเท่านั้น | ช่วยรักษาความถูกต้องของข้อมูลต้นทาง และป้องกันไม่ให้เกิดคอลัมน์ที่ไม่จำเป็นและว่างเปล่าจำนวนมาก |
| Business process หรือ grain ที่ต่างกัน | พิจารณาสร้าง fact table แยกต่างหาก ที่ยังใช้ conformed dimension ร่วมกันได้ | Process ที่ไม่ใช่การขาย เช่น การนับสต๊อกสินค้า (inventory snapshot) ไม่ควรถูกยัดเข้าไปใน `FactSales` ระดับ line-item |

ดังนั้น ต้นทางที่สามที่มีลักษณะเข้ากันได้ ควรขยายจาก mapping เดิม แทนที่จะสร้าง dimension ลูกค้า
หรือ fact table การขายแยกต่างหากสำหรับแต่ละบริษัท และต้องเป็นไปตาม contract เดิมทั้งเรื่องรหัสอ้างอิง
`SalesQuantity`, `SalesAmount`, วันที่, การจัดการ NULL และความหมายของพนักงาน

การเปลี่ยนแปลง schema ควรเป็นแบบ "เพิ่มเข้าไป" (additive) เท่านั้น ค่า `CHINOOK:<id>` และ `NORTHWIND:<id>`
เดิมต้องคงที่ไม่เปลี่ยนแปลง ข้อมูล fact เดิมของ Chinook และ Northwind ต้องไม่ถูกเขียนทับใหม่ และความหมาย
ของคอลัมน์เดิมต้องไม่เปลี่ยนไปเมื่อเพิ่มต้นทางที่สามเข้ามา

แนวทางนี้ทำให้ star schema มีความยืดหยุ่น เพราะ conformed dimension สามารถรับสมาชิกใหม่จากต้นทาง
ใหม่ที่เข้ากันได้ ในขณะที่เหตุการณ์ทางธุรกิจที่ต่างออกไปจริงๆ สามารถใช้ fact table อีกตัวได้ โดยไม่ทำให้ grain
ที่กำหนดไว้ของ `FactSales` อ่อนแอลง

## 4.3 Data Lake เทียบกับ Data Warehouse

Data Lake และ Data Warehouse ทำหน้าที่เสริมกัน ไม่ใช่แข่งกัน — Lake เก็บข้อมูลดิบหรือข้อมูลที่ยังใกล้เคียง
ต้นทางไว้อย่างยืดหยุ่น ส่วน Warehouse เผยแพร่โครงสร้างที่ผ่านการจัดระเบียบแล้ว พร้อมความหมายเชิงวิเคราะห์
ที่สอดคล้องกัน

| ประเด็น | Data Lake | Data Warehouse |
| --- | --- | --- |
| วัตถุประสงค์ | เก็บรักษาข้อมูลไว้เพื่อการนำเข้า สำรวจ ตรวจสอบ lineage และประมวลผลซ้ำ | ส่งมอบข้อมูลที่สอดคล้องกันสำหรับงานวิเคราะห์ dashboard และรายงาน |
| รูปแบบข้อมูล | ข้อมูลดิบหรือใกล้เคียงต้นทาง ทั้งแบบมีโครงสร้าง กึ่งมีโครงสร้าง และไม่มีโครงสร้าง | Fact และ dimension ที่ผ่านการจัดระเบียบและทำให้เป็นมาตรฐานแล้ว |
| Schema และการแปลงข้อมูล | โครงสร้างอาจถูกกำหนดตอนใช้งาน มักเรียกว่า schema-on-read | กฎทางธุรกิจและโครงสร้างปลายทางถูกกำหนดก่อนเผยแพร่สู่ BI มักเรียกว่า schema-on-write |
| การใช้งานทั่วไป | สำรวจข้อมูลต้นทาง วิเคราะห์ profiling ทำ mapping ใหม่ และรองรับการควบรวมกิจการใหม่ | Query ที่ทำซ้ำได้ และตัวชี้วัดที่ผ่านการควบคุมมาตรฐานสำหรับ business analyst |
| บทบาทใน OmniCorp | เก็บข้อมูล Chinook, Northwind และต้นทางในอนาคต ไว้ในรูปแบบที่ใกล้เคียงต้นทาง | เผยแพร่ star schema ที่รวมศูนย์แล้ว ซึ่งประกอบด้วย `FactSales`, `DimCustomer`, `DimEmployee`, `DimProduct`, `DimTime`, และ `DimSourceSystem` |

แนวคิดของ flow ทั้งหมดคือ:

```text
ระบบต้นทาง (Source systems)
    -> Data Lake / พื้นที่เก็บข้อมูลดิบหรือใกล้เคียงต้นทาง
    -> ตรวจสอบความถูกต้อง + ทำให้เป็นมาตรฐาน + ทำ semantic mapping
    -> Data Warehouse / conformed star schema
    -> งาน BI / รายงาน
```

Lake เก็บค่าดั้งเดิมและฟิลด์เฉพาะของต้นทางไว้ เพื่อให้ตรวจสอบหรือรันการแปลงข้อมูลซ้ำได้ในภายหลัง
ตัวอย่างเช่น ส่วนลด (`Discount`) ของ Northwind อาจยังคงอยู่ในข้อมูลที่ใกล้เคียงต้นทาง แม้ว่า warehouse
ปัจจุบันจะตั้งใจไม่นำมาคิดใน `SalesAmount` ก็ตาม

Warehouse ให้อินเทอร์เฟซการวิเคราะห์ที่เรียบง่ายกว่า ด้วย grain ระดับ line-item ของ `FactSales`,
dimension ที่ใช้ร่วมกัน, รหัสอ้างอิงมาตรฐาน และ measure ที่สอดคล้องกัน ทำให้ผู้ใช้งาน BI คำนวณตัวชี้วัด
เช่น `SUM(FactSales.SalesAmount)` ได้ โดยไม่ต้องสร้าง join ระหว่างต้นทาง Chinook และ Northwind ขึ้นมาใหม่เอง

ทั้งสองชั้นข้อมูลยังต้องการการกำกับดูแล (governance) ที่กระชับ ทั้งเรื่องความเป็นเจ้าของข้อมูล การเข้าถึง
metadata คุณภาพข้อมูล ระยะเวลาการเก็บ และ lineage โปรเจกต์ DSI310 นี้ออกแบบเฉพาะชั้นการวิเคราะห์ของ
warehouse และการ mapping ของมันเท่านั้น ไม่ได้ implement Data Lake จริงหรือแพลตฟอร์ม warehouse
ระดับ production ที่สมบูรณ์

OmniCorp สามารถใช้ Data Lake สำหรับการเก็บข้อมูลดิบหรือใกล้เคียงต้นทางอย่างยืดหยุ่น และใช้
Data Warehouse สำหรับงาน BI ที่ผ่านการจัดระเบียบและรวมศูนย์แล้ว
